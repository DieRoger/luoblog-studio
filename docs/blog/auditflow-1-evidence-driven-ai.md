# Evidence-Driven AI Is an Architecture, Not a Prompt: What AuditFlow's Code Actually Does

## Background

The phrase "evidence-driven AI" gets thrown around a lot. Most of the time it means "we told the LLM to cite its sources." That is not evidence-driven AI. Evidence-driven AI is an **architecture** — a set of structural constraints that make it impossible for an unsupported claim to reach the output.

This article is grounded in two things I actually read:
1. The real AuditFlow source code (`agents/evidence/agent.py`, `application/audit/materiality.py`, `domain/audit/entities/misstatement.py`)
2. The hallucination-detection papers actually sitting in the knowledge base (SelfCheckGPT, Chain-of-Verification, CRITIC, Teaching LMs to Support Answers)

I'm writing it because the first version of this blog was a summary of a handover document — and it was wrong in ways that reading the code exposed. This version only claims what the code and the papers actually show.

## Part 1: What the Evidence Agent Code Actually Does

The evidence agent is about 50 lines. Here is the entire prompt contract:

```python
EVIDENCE_SYSTEM = "You are an audit evidence specialist. Match claims to evidence from provided data."
EVIDENCE_PROMPT = """Claims to verify: {claims}
Available data: {data}

Return JSON:
{{"evidences": [{{"claim": "exact claim text", "matched": true/false, "source": "document reference", "confidence": 0.0-1.0}}], "coverage": 0.0-1.0}}"""
```

Three facts stand out:

### Fact 1: Evidence matching is an LLM judgment, not a retrieval operation

The agent stuffs `claims_to_verify` and a truncated `financial_data` string into a prompt, and asks the LLM to decide which claims are "matched." There is no vector search, no chunk lookup, no entailment check against a document store. The model is doing semantic judgment in its head, based on whatever context fit in the prompt.

This is important to state honestly: **the current implementation does not enforce grounding the way the architecture doc claims it does.** The handover document describes an evidence chain; the code implements a confidence judgment.

### Fact 2: The citation document_id is hardcoded

```python
citations=[Citation(claim=c.claim, document_id="evidence_source", excerpt=c.claim, confidence=c.confidence) for c in claims if c.matched]
```

`document_id="evidence_source"` is a string literal. Every matched claim gets a citation pointing at a document that doesn't exist. The excerpt is the claim itself, not the evidence text.

For an audit system, this is the difference between "the conclusion is supported by page 14 of the supplier contract" and "the conclusion is supported by a string I made up." The second one fails an audit review instantly.

### Fact 3: Orchestration is a next_action field, not a DAG

```python
return AgentResponse(
    status="SUCCESS",
    result={"artifact": artifact.model_dump(), "coverage": content.coverage},
    citations=artifact.citations,
    confidence=content.coverage,
    metrics={"evidences": len(claims), "coverage": content.coverage, "tokens": ...},
    next_action="REVIEWER_AGENT",
)
```

The agent tells the workflow "next run the reviewer." That's a linear chain encoded in each agent's return value — not a declarative DAG of dependencies. It works for a 5-agent pipeline; it would be a maintenance problem at 20 agents.

## Part 2: What the Hallucination Literature Actually Says

The knowledge base has the papers. Retrieving them returns actual chunk content, which is what I'm quoting from:

### SelfCheckGPT (2303.08896)

The abstract chunk retrieved at 0.71 similarity:

> "In this paper, we propose SelfCheckGPT, a sampling-based approach that can detect whether responses generated by LLMs are hallucinated or factual."

The core mechanism: sample the model multiple times on the same prompt, then measure **consistency across samples**. The insight is that hallucinated facts vary run-to-run while grounded facts stay stable. This is a *sampling* strategy — it never needs the ground truth or a retrieval store.

**Why this matters for AuditFlow**: the evidence agent's `confidence` field is a single LLM judgment. SelfCheckGPT suggests confidence should come from *multiple samples' agreement*, not one pass. A claim that the model states confidently in one sample but contradicts in another is a red flag that a single-pass confidence score will miss.

### Chain-of-Verification (2309.11495)

The retrieved chunk describes the CoVe pipeline step:

> "Step (2) of CoVe involves planning the verification questions. In the biography task case we split the longform generation into its individual passages..."

CoVe's structure: draft → plan verification questions → answer them independently → revise based on discrepancies. The key architectural point: **verification is a separate planning step, not an afterthought**. The model decides what to check before it checks it.

**Why this matters for AuditFlow**: the evidence agent verifies claims in one prompt. It never plans what to verify. A CoVe-style design would: extract claims → generate verification queries per claim → run each query against the data → flag mismatches. That's a structural difference, not a prompt tweak.

### CRITIC (2305.11738)

The retrieved chunk:

> "Motivated by the human process of iterative drafts refinement, we can iterate the process of verify-then-correct until specific stopping criteria are met, such as satisfying critiques from verification, reaching the maximum iterations n, or receiving environmental feedback."

CRITIC's contribution: the model critiques its own output **using external tools** — search, calculators, code execution — then corrects. The verify step is grounded in a tool's real output, not the model's memory.

**Why this matters for AuditFlow**: the evidence agent's only "tool" is the data string stuffed in the prompt. CRITIC argues the correction loop should call an actual retrieval tool to check each claim against the real document store — which is exactly the missing piece (Fact 1 and Fact 2).

### Teaching LMs to Support Answers with Verified Quotes (2203.11147, GopherCite)

The retrieved chunk describes the inline evidence syntax:

> "Our models generate an answer with supporting evidence 'inlined' into a single string (hence 'Inline Evidence'), treating the task of producing supported claims as (conditional) language modelling. Answer and evidence use the following template..."

And the human rating design:

> "The claim is shown in a blue box representing chat message, and the evidence is shown in a grey call-out box, presenting page title and the quoted fragment."

GopherCite's crucial design decision: **evidence is a quoted fragment with a page title, presented separately from the claim** — and it's trained with a human reward for *verified* quotes. The quote must be verbatim from a real source; the model is penalized for unverifiable quotes.

**Why this matters for AuditFlow**: this is the strongest argument that AuditFlow's hardcoded `document_id="evidence_source"` is not just a code smell — it's a design contradiction. GopherCite treats "the quote exists in a real source" as the entire point. AuditFlow's evidence agent currently emits the claim itself as the "excerpt," which GopherCite's rating interface would reject immediately.

## Part 3: Where the Real Domain Knowledge Lives

Not everything is broken. The MaterialityEngine and Misstatement code are genuinely good domain encoding.
### MaterialityEngine (ISA 320)

```python
ISA_PERCENTAGES = {
    "profit_before_tax": 0.05,   # 5% of PBT
    "revenue": 0.005,            # 0.5% of revenue
    "total_assets": 0.01,        # 1% of total assets
    "equity": 0.01,              # 1% of equity
}
RISK_ADJUSTMENT = {"LOW": 1.0, "MEDIUM": 0.75, "HIGH": 0.5}
```

The critical decision is the selection rule:

```python
# 选最低值作为整体重要性（最保守原则）
non_zero = {k: v for k, v in bases.items() if v > 0}
base_metric = min(non_zero, key=non_zero.get) if non_zero else "revenue"
```

An auditor computes materiality from four bases and takes the **minimum** — because underestimating materiality is the safe direction. If you think $50K matters and it's actually $100K, you've over-tested (wasteful but safe). If you think $100K matters and it's actually $50K, you've under-tested (dangerous). The `min()` is one line, but it encodes a century of professional risk aversion.

Risk adjustment compounds this: a HIGH-risk engagement cuts performance materiality in half (0.5 multiplier), forcing more audit work exactly when the risk is highest.

### Misstatement classification

```python
class MisstatementType(Enum):
    KNOWN = "KNOWN"        # 已确认
    LIKELY = "LIKELY"      # 可能（样本推断总体）
    PROJECTED = "PROJECTED"  # 统计推断
    JUDGMENTAL = "JUDGMENTAL"  # 会计估计差异
```

The four-way classification (Known/Likely/Projected/Judgmental) is the standard audit framework, and the entry types (AJE/RJE/PJE) map to how the adjustment is booked. The demo's "$215K known → exceeds $50K tolerable → 4 AJE" flow only works because this classification exists — you can't decide whether an adjustment is required without knowing whether the misstatement is known or merely projected.

### Evidence Graph: the one place the architecture and code agree

The Evidence Graph domain (`domain/audit/entities/evidence_graph.py`) is the counter-example to the Evidence Agent's problems. Its module docstring states the division of labor explicitly:

```python
"""Evidence Graph Domain — Assertion → Evidence → 充分性判定
LLM 负责找证据，Graph 负责判断充分性。"""
```

"LLM finds the evidence; the Graph judges sufficiency." This is the correct separation: the LLM is a *producer*, the deterministic graph is the *judge*. The assertion node encodes exactly which evidence types are required, and the conclusion is computed, not guessed:

```python
class AssertionConclusion(Enum):
    SATISFIED = "SATISFIED"
    PARTIALLY_SATISFIED = "PARTIALLY"
    NOT_SATISFIED = "NOT_SATISFIED"

def conclusion(self) -> AssertionConclusion:
    present = sum(1 for e in self.evidence_nodes
                  if e.status == EvidenceStatus.PRESENT
                  and e.evidence_type in self.required_evidence_types)
    total = len(self.required_evidence_types)
    if present == total:
        return AssertionConclusion.SATISFIED
    # ... partial / not-satisfied logic
```

The demo result — `CUTOFF 50%, OCCURRENCE 33% → PARTIALLY SATISFIED` — is a deterministic calculation: 2 of 4 required evidence types present for cutoff, 1 of 3 for occurrence. No LLM involved. This is what "evidence-driven" should mean: the judgment about *sufficiency* is a hard computation over a typed evidence model, and the LLM's job is limited to finding the evidence items.

The gap in Part 1 is now sharper: the Evidence Agent produces `matched: true/false` judgments with no document linkage, while the Evidence Graph expects `EvidenceNode` with `document_no`, `source_ref`, and an evidence type from a controlled set. The two modules speak different languages. The agent's hardcoded `document_id="evidence_source"` cannot feed the graph's `source_ref` requirement.

### Sampling Engine: reproducibility is a feature

`application/audit/sampling.py` implements three sampling methods — ALL, RANDOM, and MUS (monetary unit sampling):

```python
rng = random.Random(42)  # 固定种子保证可复现
```

The hardcoded seed is a deliberate engineering decision worth highlighting. Audit sampling must be reproducible — if a reviewer asks "which transactions did you sample and why," the answer has to be regenerable, not "we ran it and this is what came out." `random.Random(42)` makes the sample deterministic across runs.

MUS is the interesting method: the larger the monetary value, the higher the selection probability. This is the standard audit technique for catching material misstatements — a $10 error in a $1M transaction matters more than a $10 error in a $100 transaction, so MUS biases sampling toward big-ticket items. The implementation computes cumulative amounts and samples proportionally.

These two pieces — deterministic seed and monetary weighting — are exactly the kind of detail a handover document summarizes as "we have a sampling engine" but that a reader needs the code to appreciate.

## Part 4: The Gap Between the Architecture and the Code

Putting Parts 1-3 together exposes a coherent gap:
| Layer | Architecture says | Code does | Literature says |
|-------|------------------|-----------|-----------------|
| Evidence matching | Retrieval → verify | LLM judgment on prompt data | CRITIC: verify with tools |
| Citation | Chain to document | Hardcoded `evidence_source` | GopherCite: verbatim quote + page |
| Confidence | Retrieval score | Single LLM confidence | SelfCheckGPT: multi-sample consistency |
| Verification plan | — | Single-pass match | CoVe: plan questions first |
| Domain logic | ISA-compliant | ✅ Genuinely good | — |

The first four rows are the evidence-grounding gap. The last row — the domain logic — is where the code is actually ahead of the literature: there is no paper that encodes ISA 320 materiality the way MaterialityEngine does, because that's professional knowledge, not model behavior.

## Part 6: What the Fix Looks Like

The gap analysis suggests a concrete, literature-aligned fix for the evidence agent. It has four parts, each mapped to a paper:

### 1. Extract → Plan → Verify (CoVe)

Replace the single "match these claims to this data" prompt with a three-step pipeline:

```
Step 1 (extract):  claim = extract_claims(report_text)
Step 2 (plan):     queries = plan_verification_queries(claim)  # what to check
Step 3 (verify):   result = retrieve_and_check(query)          # against real store
```

CoVe's contribution is Step 2 — the model decides what would falsify the claim before checking it. For audit, a claim like "revenue was recognized prematurely" should generate verification queries like "which transactions have invoice dates after the period end?" — and those queries should be answered by data, not by the model's memory.

### 2. Verify with tools, not memory (CRITIC)

The verify step needs a tool call: query the transaction store, run the search, get back the actual records. CRITIC's "verify-then-correct" loop would then compare the claim against the retrieved records and flag mismatches. This is structurally different from stuffing `financial_data[:800]` into a prompt — the tool returns ground truth, the model only interprets it.

### 3. Confidence from consistency, not one pass (SelfCheckGPT)

Replace the single `confidence` float with a consistency check: run the verification twice (different temperatures or samples) and measure agreement. A claim the model verifies identically twice is more trustworthy than one it verifies once with 0.85. The cost is one extra LLM call per claim — cheap insurance for an audit system.

### 4. Citations from real documents (GopherCite)

The hardcoded `document_id="evidence_source"` gets replaced with the actual retrieved document reference: page, paragraph, and verbatim quote. GopherCite's inline-evidence format is the model:

```text
Answer: <answer text>
Evidence: <page title> — "<verbatim quote from the source>"
```

The verification gate: a citation is only emitted if the quote exists in the retrieved chunk. If it doesn't, the claim is downgraded to unsupported and blocked from the report.

### Why the Evidence Graph is the right foundation

The Evidence Graph already provides the deterministic layer: `AssertionNode.conclusion()` computes SATISFIED/PARTIALLY/NOT_SATISFIED from typed evidence nodes. The fix isn't to add more LLM judgment — it's to feed the graph real evidence nodes (with `document_no` and `source_ref`) instead of the agent's unlinked `matched` flags. The graph already knows how to judge sufficiency; it just needs the evidence to be real and locatable.

## Lessons Learned

1. **Read the code before writing about the system.** The handover document described an evidence chain that the code doesn't implement. Every "architecture description" in a blog should be verifiable against a `grep` — and if it isn't, the blog is fiction.
2. **A hardcoded citation ID is a design contradiction, not a TODO.** In an evidence-driven system, "the source" is the entire point. `document_id="evidence_source"` means the system currently cannot answer the question an auditor will ask first: *where does this come from?*
3. **Confidence from one pass is not confidence.** SelfCheckGPT's multi-sample consistency is the cheap, principled upgrade to a single-pass confidence score. It's also embarrassingly easy to add: run the claim-matching prompt twice, compare.
4. **Verification needs a plan and tools.** CoVe plans what to check; CRITIC checks with tools. A single prompt that does "match these claims to this data" is neither. Both papers point to the same architectural fix: extract → query → verify → correct.
5. **Domain code can be better than the papers.** MaterialityEngine's `min()` conservative rule and the Known/Likely/Projected/Judgmental taxonomy are professional knowledge encoded correctly. The papers don't help here — only the domain does. This is why evidence sources must include code and domain docs, not just papers.

## Key Takeaways

- **Evidence-driven AI is structural: unsupported claims must be impossible to emit.** Prompt instructions are not enforcement.
- **The gap between architecture docs and code is where hallucination lives.** Read the code; the doc will mislead you.
- **SelfCheckGPT (multi-sample), CoVe (plan verification), CRITIC (verify with tools), GopherCite (verbatim quotes) all point to the same fix**: extract claims → verify each against a real source with a tool → emit only what's verified.
- **Hardcoded citation IDs fail the auditor's first question.** If the source isn't real and locatable, the "evidence" doesn't exist.
- **Domain knowledge (ISA 320 materiality) is a first-class evidence source.** Papers cover model behavior; code covers professional judgment. Both are needed.
- **Deterministic domain logic is the model for what AI verification should become.** The Evidence Graph's `conclusion()` is computed, not guessed — the LLM's role is to produce inputs for that computation, not to replace it.

## What I'd Do Differently Next Time

If I were starting this analysis over, I would:

1. **Grep first, document later.** The handover document was the wrong primary source. The correct order is: read the code, then read the doc, then write — with the code as ground truth.
2. **Measure the gap quantitatively.** I can say "the agent doesn't link citations," but I haven't measured how often. A quick evaluation — take 10 claims, run the agent, count how many citations resolve to real chunks — would turn an anecdote into a number.
3. **Test the paper-based fix before writing about it.** Part 6 proposes a CoVe-style pipeline. It's plausible and literature-aligned, but it's untested in this codebase. The honest next step is a small experiment, not a confident claim.

This is the same lesson the evaluation-driven work in AuditFlow taught: a claim without a benchmark is a hypothesis.
