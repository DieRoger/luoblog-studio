# 20 Bugs in 184 Tests: What Principal Engineer Reviews Found That CI Missed

## Background: The Illusion of Green Tests

A passing test suite is a necessary condition for code quality, but it is far from sufficient. In a Python backend with 21 modules, 184 tests, and roughly 12,000 lines of code, all tests executed cleanly in under three seconds [Source: LuoBlog Studio | Section: Stats]. The architecture followed Clean Architecture principles: API → Service → Domain ← Infrastructure, with the Domain layer containing zero framework imports [Source: LuoBlog Studio | Section: Stats]. Despite this well-structured foundation, a principal engineer review uncovered 20 distinct bugs that the green test suite had completely missed. This gap between test coverage and real-world correctness is a classic illusion—tests pass not because the system is correct, but because they verify the wrong things.

The review found that many tests were passing due to shallow assertions or missing edge cases. For example, the CJK chunking bug used an English-only regex pattern, so tests with only ASCII input passed without issue [Source: LuoBlog Studio | Section: Bugs]. Similarly, the fake async in PdfParser meant that tests never actually exercised the asynchronous behavior, and the lazy import mock contamination caused test isolation failures that silently propagated state between unrelated test cases [Source: LuoBlog Studio | Section: Bugs]. These are not exotic edge cases—they are common engineering pitfalls that a well-designed test suite should catch. The fact that 7 bugs were found in just 14 passing tests within the Writing Agent pipeline further underscores the pattern: serial calls, missing retry logic, and absent system prompts all slipped through because the tests never simulated real-world concurrency or error recovery [Source: LuoBlog Studio | Section: Architecture].

The practical takeaway is that green tests are a baseline, not a guarantee. To break the illusion, engineers must design tests that stress the boundaries of the system—test with non-ASCII input, verify async behavior with actual delays, and isolate mocks per test case to prevent contamination. A principal engineer review adds value precisely because it applies human judgment to identify what the test suite’s assumptions are missing. In this case, the review found that the test suite was optimizing for speed (3 seconds) at the cost of depth. The solution is not to write more tests, but to write better ones—tests that challenge the system’s real behavior, not just its happy path.

## Implementation Details: 20 Bugs That Slipped Through CI

The most alarming finding from the principal engineer review was not the existence of bugs, but that all 184 tests passed in ~3 seconds while 20 distinct defects remained hidden [Source: LuoBlog Studio | Stats]. This suggests a fundamental gap between what CI validates and what production actually requires. The review uncovered seven bugs in a single component—the Writing Agent pipeline—despite all 14 of its tests passing. These included serial API calls where parallel execution was expected, a complete absence of retry logic for transient failures, and a missing system prompt injection that silently degraded output quality [Source: LuoBlog Studio | Architecture]. The tests passed because they mocked network calls and used trivial input lengths, never exercising the concurrency, recovery, or prompt composition paths that would fail in production.

The remaining 13 bugs clustered around cross-cutting concerns that individual unit tests cannot catch. The CJK chunking bug used an English-only regex pattern, breaking text segmentation for Chinese, Japanese, and Korean content [Source: LuoBlog Studio | Bugs]. A path traversal vulnerability in DocumentStorage accepted user-supplied filenames without sanitization, yet the test suite only used safe, hardcoded paths. The PdfParser was marked as `async` but performed blocking I/O via a thread pool, making it fake async. The Embedding service had no batch size parameter, causing OOM errors on large document sets. A metadata field name conflicted with a SQLAlchemy reserved keyword, and lazy import mock contamination meant that mocks from one test leaked into another, silently passing assertions that should have failed [Source: LuoBlog Studio | Bugs].

The practical takeaway is that CI passing in three seconds with 184 tests is a red flag, not a badge of honor. These tests validated isolated functions but never composed behaviors, never tested with realistic data volumes, and never ran in parallel or under failure conditions. The engineering remedy is to add integration tests that exercise the full pipeline with CJK text, large payloads, and actual async I/O, and to enforce that mocks are scoped per test with cleanup hooks. Without these, CI becomes a false confidence generator—fast, green, and wrong.

## Lessons Learned: What Reviews Catch That Tests Miss

The most humbling realization from this review was not that bugs existed, but that they thrived in code where all 184 tests passed in under three seconds [Source: LuoBlog Studio | Section: Stats]. A principal engineer’s review of the Writing Agent pipeline, for instance, uncovered seven distinct bugs despite all 14 pipeline tests passing green. The root cause was a mismatch between test coverage and real execution paths. The tests validated individual components in isolation—serial calls worked fine when mocked, but the production pipeline used `asyncio.gather` for parallel writes, which introduced race conditions on shared state. Similarly, the tests never verified retry logic for API failures, nor did they check that the system prompt from `agents/prompts/writing/system.md` was actually injected into the LLM call. The tests passed because they tested what the code did, not what it was supposed to do [Source: LuoBlog Studio | Section: Architecture].

The review also exposed bugs that tests could not realistically catch without adversarial input. A CJK chunking bug used an English-only regex, so chunking tests with ASCII text passed perfectly, but a reviewer immediately flagged that any Chinese, Japanese, or Korean text would produce garbled boundaries. A path traversal vulnerability in `DocumentStorage` was invisible to tests that only used safe filenames—no test tried `../../etc/passwd`. The `PdfParser` declared itself async but ran synchronous calls inside `run_in_executor`, making the async wrapper a no-op that would block the event loop under load. The `Embedding` service was missing a batch size parameter, meaning it would silently fail on any input exceeding the model’s token limit. And the metadata handling used SQLAlchemy column names that conflicted with reserved keywords—a bug that only surfaced when the database schema was actually migrated [Source: LuoBlog Studio | Section: Bugs].

The practical takeaway is that tests and reviews are complementary, not redundant. Tests confirm that code executes without crashing under expected inputs; reviews validate that code handles unexpected inputs, respects architectural boundaries, and won’t fail in production. The Clean Architecture design—where Domain has zero framework imports—made these reviews more effective because reviewers could focus on business logic without wading through framework boilerplate [Source: LuoBlog Studio | Section: Stats]. Any team relying solely on a green CI pipeline should schedule a principal-level review before every major release, targeting exactly the edge cases that tests are least likely to write: internationalization, security, concurrency, and silent failures.

## Conclusion: Building a Culture of Quality Beyond CI

The most dangerous assumption in modern software engineering is that a green CI pipeline guarantees production readiness. Our principal engineer review of the Writing Agent pipeline revealed 20 distinct bugs across 184 tests that all passed in under three seconds [Source: LuoBlog Studio | Stats]. These weren’t edge cases—they included serial calls where parallelism was assumed, missing retry logic on external API calls, and a complete absence of the system prompt in agent invocations [Source: LuoBlog Studio | Architecture]. The tests were fast, deterministic, and entirely useless for catching logical defects. The core issue was not test coverage but test design: every test verified isolated units with mocked dependencies, none exercised the actual async orchestration or the interaction between agents and their system prompts.

A culture of quality beyond CI requires shifting from “does it pass?” to “does it fail meaningfully?”. Consider the CJK chunking bug: the regex was written for English-only word boundaries, yet all 184 tests used ASCII text [Source: LuoBlog Studio | Bugs]. The path traversal in DocumentStorage was invisible because test inputs were sanitized by convention, not by code. The fake async in PdfParser—a synchronous I/O call wrapped in `async def`—passed every test because no test measured wall-clock time or checked for event loop blocking. These bugs share a common root: tests that validate structure but not behavior. The principal engineer review found them by asking “what happens when this runs in production with real data?” instead of “does this mock return the expected value?”.

Building this culture demands explicit architectural constraints. Our Clean Architecture enforces that the Domain layer imports zero frameworks [Source: LuoBlog Studio | Stats], which makes domain logic testable without infrastructure. But tests must also cross architectural boundaries: integration tests that run the full agent pipeline with real LLM calls (cached for repeatability), property-based tests that generate CJK and Unicode inputs, and stress tests that verify timeout and retry behavior. The practical takeaway is this: a passing test suite is a necessary but insufficient condition for quality. The principal engineer review caught 20 bugs because it tested the system’s actual failure modes, not just its happy paths. Your CI should report not only test pass rates but also the number of untested edge cases, the ratio of unit to integration tests, and the mutation score of your domain logic. Quality is not a pipeline status—it is a design constraint that must be engineered from the start.

## Key Takeaways

1. **A structured review finds what tests miss.** All 184 tests passed. Reviews found 20+ bugs — path traversal, race conditions, CJK encoding, async violations.
2. **Test data diversity is not optional.** English-only test data hides bugs that only appear with CJK text. Add at least one non-Latin test case per text-processing module.
3. **Fake async is worse than sync.** async def that never awaits misleads callers. Either make it sync or wrap the blocking call.
4. **Mock contamination is a real CI problem.** Shared sys.modules mocks cause cross-test failures that are non-deterministic. Use @patch per test.
5. **Review checklists should include AI Reliability and Production Readiness.** Most bugs weren't logic errors — they were missing retries, missing system prompts, and untracked token costs.
